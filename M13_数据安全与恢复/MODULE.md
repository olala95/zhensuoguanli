# M13 数据安全与恢复

> 阶段：第五阶段（F90/F92/F94 的核心部分已上移第一阶段交付）
> 依赖：M12（审计）、M14（备份目录、健康检查、诊断）、所有业务模块（恢复会整体回滚）
> 被依赖：无（兜底模块）

---

## 1. 模块职责

保证**数据不丢、坏了能恢复、崩了能自愈**：自动/增量/手动备份、数据恢复、完整性检查、
SQLite 异常恢复、崩溃恢复，以及两个外部进程（AI Worker / Hardware Agent）的看门狗。

> 单机单用户诊所没有运维人员，任何恢复动作都必须**一键可完成、全程留痕、绝不静默失败**。

## 3. 模块级规则

**R-M13-1 备份优先于一切写操作。** 迁移前、恢复前、安全退出前**必须**先备份；备份失败要
明确告警，不静默继续。

**R-M13-2 备份必须可验证。** 每个备份文件记录大小 + SHA256 + 打开校验结果；不可用的备份
**标记为无效并告警**，绝不让用户恢复到一个坏文件。

**R-M13-3 恢复是高风险操作。** 恢复前自动备份当前库（防止误恢复），恢复后跑完整性检查，
全程写 `audit_high_risk`（RISK_RESTORE / RISK_BACKUP_RESTORE）。

**R-M13-4 增量是快照式的。** 全量与增量文件**同构**，都是 `VACUUM INTO` / `backup API`
产出的一致快照；增量只是登记类型不同并挂在所属全量之下，
**换取的是 RPO（恢复点间隔）而不是存储空间**。因此任一备份点都能独立恢复，
不需要回放链（详见 F91 R1 的方案取舍说明）。

**R-M13-5 怀疑损坏即进入只读。** 一旦捕获 SQLITE_CORRUPT / IOERR / integrity_check 失败，
立刻 `db.set_readonly(True)`，禁止继续写入造成二次破坏（05 §5）。

**R-M13-6 崩溃自愈不留半成品。** 启动时检测 WAL 残留与未完成任务（导入/打印/AI），
把"半截"的任务标记为失败，数据本身由事务保证干净。

**R-M13-7 看门狗只做"拉起与收敛"，不做业务补偿。** 超时任务标记失败并把可重试任务重新
入队；**绝不自动重跑已产生资金/库存影响的业务**（收费、发药）。

**R-M13-8 一切有痕。** 备份、恢复、完整性检查、崩溃恢复、看门狗重启全部落表 + 审计，
可事后追溯"什么时候、谁、恢复了哪一个文件"。

## 4. 状态与周期

| 项 | 约定 |
|---|---|
| 全量备份 | 每日首次启动自动 + 迁移前 + 手动 |
| 增量备份 | 配置 `backup.incremental_minutes`（默认 60），且必须存在同链全量 |
| 保留策略 | 全量保留 `backup.keep_days`（默认 30）天，增量随其所属全量一起清理 |
| 完整性检查 | 每次备份后 + 每次启动自检 + 手动 |
| 看门狗周期 | AI `ai.watchdog_seconds`（默认 120），硬件 `hardware.heartbeat_seconds`（默认 60） |

---

## 5. 对外接口

| 接口 | 说明 | 消费方 |
|---|---|---|
| `backup.full_backup(reason)` | 全量备份（已交付 F90/F92） | 启动流程、迁移、退出 |
| `backup.incremental_backup()` | 增量（WAL 归档，F91） | 定时任务 |
| `restore.from_backup(file)` | 从备份恢复（F93） | UI（管理员） |
| `integrity_check_now()` | 完整性检查（F94） | 启动自检 |
| `selftest.detect_crash()` | 崩溃检测（F96） | 启动流程 |
| `m13.watchdog_ai()` / `m13.watchdog_hardware()` | 看门狗（F97/F98） | 定时任务 / 手动 |
