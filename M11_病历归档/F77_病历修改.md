# F77 病历修改

[TYPE: FEATURE] [PRIORITY: P0] [SIZE: M]

---

## 1. 职责

已确认病历的**唯一修改路径**：新建版本 + 记录修改原因与时间，原版本完整保留。禁止直接编辑已确认内容（03 §2.3）。

---

## 2. 依赖

- 依赖：F76（版本）、F80（Hash 链）、M03（内容读写经其服务接口）
- 被依赖：UI 病历修改入口

---

## 3. 涉及的表

`record_amendment`、`record_version`、`record_hash`

---

## 4. 规则

**R1 只有 CONFIRMED 可修改留痕。** `DRAFT` 直接编辑（M03）；`ARCHIVED` / `SEALED` **不得修改**（需先解封，F82）。

**R2 必填修改原因。** 写明"改了什么 + 为什么"；原因长度不足拒绝（E2001）。

**R3 内容写入经 M03 接口，且快照必须反映新内容。** 事务内顺序：读取原值 → 经 `m03_record.apply_amendment()` 落新内容 → 建新版本（**新快照**）→ 续写 Hash → 写 `record_amendment` 留痕。任一步失败整体回滚。

> 说明：原顺序（先建版本后落内容）会让版本快照停留在改前内容，导致「版本 v2 与当前内容不一致」，故调整为快照在内容之后生成；留痕与版本仍在**同一事务**内，原子性不受影响。

**R4 留痕含前后对比。** `field_path`（哪个字段/哪一段）+ `before_value` + `after_value`，便于追溯。

**R5 修改人必记。** 记录操作人、角色、时间；**代他人修改尤其要留痕**（与签名一致的责任链）。

**R6 封存后禁止。** `SEALED` 病历拒绝修改（E3001），必须先解封并写高风险审计。

**R7 一次可改多处。** 一次留痕可包含多条 `field_path` 变更，但只生成一个新版本（避免版本爆炸）。

---

## 5. 验收标准

**AC1（修改生成新版本且旧版本保留）**
- Given v1 已存在
- When 走修改留痕
- Then 生成 v2，v1 仍在且内容不变
- 验证方式：自动

**AC2（原因必填）**
- Given 未填原因
- When 提交修改
- Then 拒绝 E2001
- 验证方式：自动

**AC3（留痕含前后值）**
- Given 把主诉从"咳嗽三天"改为"咳嗽五天"
- When 查 `record_amendment`
- Then 一条记录含 before/after
- 验证方式：自动

**AC4（封存后禁止修改）**
- Given 病历已 SEALED
- When 提交修改
- Then 拒绝 E3001
- 验证方式：自动（跨 F81）

**AC5（整体回滚）**
- Given 建版本成功但内容写入失败
- When 查版本与留痕
- Then 均未落库（同事务）
- 验证方式：自动（注入失败）

**AC6（修改人留痕）**
- Given 医生 B 修改了医生 A 的病历
- When 查留痕
- Then 操作人为 B，含角色与时间
- 验证方式：自动

## 6. 异常码

| 码 | 场景 | 可重试 |
|---|---|---|
| E2001 | 修改原因缺失 | 否 |
| E3001 | 状态不允许修改（已归档/已封存） | 否 |
| E6002 | 无修改权限 | 否 |

---

## 7. 失败恢复

| 失败点 | 恢复方式 |
|---|---|
| 事务中断 | 整体回滚，可重新提交 |
| 内容写入失败 | 不留半成品版本（R3） |
