# M11 病历归档

> 阶段：第四阶段
> 依赖：M03（病历 record 及全部内容表，只读 + 经其服务接口确认状态）、M02（Visit）、M12、M14
> 被依赖：无（链路末端）

---

## 1. 模块职责

病历确认之后的**全生命周期管理**：版本化 → 修改留痕 → 关闭 → 归档（按月，带归档号）→ Hash 链 → 封存 → 解封 → 导出。

> 与 M03 的边界：M03 负责**写**病历（主诉/现病史/诊断等）与确认签名；本模块负责确认**之后**的版本、归档与封存。**本模块不修改病历内容**。

---

| 表 | 职责 |

| `record_export` | 导出记录（F83） |

## 3. 模块级规则

**R-M11-1 确认后不可直接编辑。** `CONFIRMED` 之后任何内容修改走 F77：新建版本 + 记录修改原因与时间，**原版本完整保留**（03 §2.3）。

**R-M11-2 Hash 链不可断。** 每个版本写入 `record_hash`：`hash = sha256(规范序列化(版本快照) + prev_hash)`；首条 `prev_hash` 为空串。校验时逐条重算，任一不符即发现篡改。

**R-M11-3 归档按月。** 归档号 `AR{yyyyMM}{4位}`（契约 §1.2）；同一份病历只归档一次。

**R-M11-4 封存即冻结。** `SEALED` 后不得修改、不得再归档；只能解封（F82），且**解封写高风险审计**（03 §9）。

**R-M11-5 解封必填原因与责任人。** 解封是敏感动作：原因、操作人、时间全部留痕，解封记录永久保留（封存行不删）。`UNSEALED` 本身不可再封存，需**重新归档开新归档号**后才能封存。

**R-M11-6 管理员无权改内容。** 管理员可封存/解封/导出，**不能修改已确认病历内容**（03 §9）。

**R-M11-7 版本快照自包含。** 每个版本保存完整快照（JSON 序列化后的病历内容），**不依赖后续内容变更**（否则历史版本会被"追溯改写"）。

**R-M11-8 导出不落内容副本。** `record_export` 只记录导出事件与目标路径/格式，**不复制病历内容**（避免第二份事实来源）。

**R-M11-9 幂等。** 归档、封存、导出均支持 `idempotent_key`，防重复。

**R-M11-10 只读上游数据。** 需要病历内容时通过 M03 的服务接口读取，**不直接写 M03 的表**（R2）。

## 4. 状态机引用

```
DRAFT → CONFIRMED（M03 F19 确认，同时建 v1 + Hash 链首条）
CONFIRMED → ARCHIVED（F79 归档，开 AR{yyyyMM}{4位}）
ARCHIVED → SEALED（F81 封存）
SEALED → UNSEALED（F82 解封，高风险）
UNSEALED → ARCHIVED（F79 重新归档，开**新**归档号；更正后可再次封存）
```

> UNSEALED 不是"死路"：解封的目的是更正，更正后必须**重新归档（新归档号）**再封存，
> 使"封存—解封—再封存"形成可审计的成对记录，而不是原地反复冻结。
另有 **F78 病历关闭**：`closed` 标记（在归档前，表示不再接受修改），不新增契约状态。
