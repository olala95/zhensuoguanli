## 1. 端到端场景

### S1 新患者首次就诊全流程（F01 → F02 → M02）
1. 接诊台搜索"李四" → 无结果
2. 建档：录入姓名、性别、出生日期、手机号（刷身份证自动填充更快）
3. 点击"保存并开就诊"
4. 进入 M02 创建 Visit

**通过标准**：建档不阻塞（最小必填）；重复检测生效；一步衔接开就诊；全程有审计。

### S2 复诊患者快速定位（F02 → F03）
1. 打开接诊界面，搜索框为空即显示今日已就诊患者
2. 输入"张"模糊搜索 → 定位到"张三丰"
3. 查看其资料：3 次就诊、5 张处方、2 笔账单
4. 补充一个备用电话
5. 点击某张历史处方跳转查看

**通过标准**：默认列表按就诊时间倒序；搜索响应 < 300ms；历史概览只读；补充电话有审计。

### S3 重复患者合并（F04 → 各模块）
1. 检测发现两名"王五"（身份证一致）
2. 预览：次患者名下 3 就诊 / 5 处方 / 2 账单，其中 1 份已归档病历
3. 字段对比：性别一致、联系方式不同、无身份证冲突
4. 填原因 → 二次确认 → 执行合并
5. 验证：全部未归档单据改挂、联系方式并集保留、已归档病历保留在原患者、日志完整

**通过标准**：无单据丢失；无半成品；日志可完整追溯；次患者不可再建就诊。

## 2. 故障场景（本模块专属）

### FA1 建档中途崩溃
- 操作：建档提交过程中强杀进程
- 期望：患者记录要么完整（含联系人与审计）要么不存在
- 通过标准：无半条患者；重启后重新建档成功且患者号不重复

### FA2 合并执行中途崩溃
- 操作：合并改挂到一半强杀进程
- 期望：整体回滚，主次患者均回到合并前状态
- 通过标准：**绝不出现部分改挂**（这是本模块最危险的失败模式）

### FA3 身份证读卡器不可用
- 操作：mock 读卡器失败后建档
- 期望：完全手工录入可用，不阻塞
- 通过标准：建档成功，`id_verified=0`

### FA4 患者改名后的快照一致性
- 操作：患者有历史处方后修改姓名
- 期望：历史处方中的患者快照不变
- 通过标准：跨模块数据一致，归档原则未被破坏

## 3. 跨模块契约检查

| 检查项 | 期望 |
|---|---|
| 快照机制 | 处方/账单/归档病历存患者快照，不随主数据变更 |
| 改挂接口 | 合并通过 `patient.reassign()` 完成，无直接写他模块表 |
| 已归档处理 | 已归档病历不改挂，且预览中明确提示 |
| 敏感脱敏 | 列表中身份证/手机号脱敏；查看完整号码有审计 |
| 审计完整 | 建档、修改、作废、合并全部有审计；合并有 `audit_high_risk` |
| 删除保护 | 有业务数据的患者不可删除 |
