# F84 操作审计

[TYPE: FEATURE] [PRIORITY: P0] [SIZE: M]

---

## 1. 职责

记录每一次业务操作：谁、以什么角色、在哪个模块功能点、对什么对象、做了什么、结果如何、来源是什么。

---

## 2. 依赖

- 依赖：M14（`auth.currentUser()` 提供操作人与角色上下文）
- 被依赖：**全部模块**

---

## 3. 涉及的表

`audit_operation`（M12 自有，**只允许 INSERT**）

---

## 4. 规则

**R1 必记字段。** 每条记录含：

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `operator_id` / `operator_role` | 操作人 ID 与**当时激活的角色** |
| `module` / `feature` | 模块名（M06）与功能点编号（F34） |
| `action` | 动作（create / update / confirm / void / dispense …） |
| `target_type` / `target_id` | 对象类型（`prescription`）与 ID 或单号 |
| `result` | success / failure |
| `error_code` | 失败时的异常码 |
| `source` | UI / AI / Hardware / IPC / System |
| `ai_confirmed_by` | 来源为 AI 时的确认人（见 R5） |
| `audited_at` | **系统时间**，不接受外部传入 |
| `context` | JSON 补充上下文（不含敏感原文） |

**R2 审计失败 → 业务回滚（R-M12-3）。** 审计写入失败时整个业务事务回滚，抛 `E1010`。**绝不允许无审计的业务操作落库。**

**R3 同事务。** 业务写入与审计写入在同一数据库事务内（R-M12-4）。

**R4 禁止修改与删除。** 触发器拦截 UPDATE/DELETE；应用层同样拦截。删除尝试记 `audit_high_risk` + 告警。

**R5 AI 来源必须标记确认人。** 来源为 `AI` 时，必须同时记录 `ai_confirmed_by`（确认的医生 ID）。没有确认人的 AI 操作不得直接落业务库。

**R6 批量操作逐条记。** 批量操作（如批量导入）记录一条汇总 + 明细条数，不逐条膨胀审计表；但**业务单据级别**操作（每张处方、每笔收费）必须逐条记。

**R7 覆盖检查机制。** 提供"审计覆盖自检"工具：扫描全部业务表，列出"有写操作但无对应审计埋点"的表。该工具在阶段门禁时运行。

**R8 敏感值不入库。** 密码、密钥不进审计；身份证后 4 位 + 哈希；不记录大段文本原文（病历内容变更走 F85 的字段级前后值）。

## 5. 验收标准

**AC1（基本记录）**
- Given 医生 A 以"医生"角色确认一张处方 R202610090012
- When 操作完成
- Then `audit_operation` 新增一条：operator=A、role=医生、module=M06、feature=F37、action=confirm、target=prescription/R202610090012、result=success、source=UI、audited_at 为系统时间
- 验证方式：自动

**AC2（失败也记录）**
- Given 一次因库存不足而失败的发药操作
- When 操作失败
- Then `audit_operation` 仍新增一条，result=failure，error_code=E3xxx
- 验证方式：自动

**AC3（审计失败阻断业务）**
- Given 模拟 `audit_operation` 写入失败（如触发器注入异常）
- When 执行一笔收费
- Then 收费事务整体回滚，返回 `E1010`，**数据库中无该笔账单**
- 验证方式：自动

**AC4（不可修改）**
- Given 已存在审计记录
- When 尝试 UPDATE 或 DELETE
- Then 被拒绝（触发器与应用层双重拦截），并新增一条 `audit_high_risk` 记录该尝试
- 验证方式：自动

**AC5（时间不可外部指定）**
- Given 调用方传入一个伪造的时间参数
- When 写入审计
- Then `audited_at` 仍为真实系统时间，忽略传入值
- 验证方式：自动

**AC6（AI 来源标记确认人）**
- Given AI 生成处方建议，医生 B 采纳
- When 落库
- Then `source=AI` 且 `ai_confirmed_by=B`
- 验证方式：自动

**AC7（AI 无确认人不得落库）**
- Given AI 生成草稿
- When 尝试在无人确认的情况下写入业务表
- Then 被拒绝，返回 `E6002`（或专用码），无业务数据落库
- 验证方式：自动

**AC8（角色随会话变化）**
- Given 用户先以"医生"后切换为"收费员"
- When 分别执行两类操作
- Then 两条审计的 `operator_role` 分别为"医生"和"收费员"
- 验证方式：自动

**AC9（审计覆盖自检）**
- Given 系统中存在一张故意未加埋点的测试业务表
- When 运行覆盖自检工具
- Then 该表被列入"缺失审计埋点"清单
- 验证方式：自动

**AC10（性能）**
- Given 单次业务操作
- When 计入审计写入
- Then 额外耗时 < 20ms；连续 1000 次操作审计写入不影响可用性
- 验证方式：自动（性能断言）

---

## 6. 异常码

| 码 | 场景 | 可重试 |
|---|---|---|
| E1010 | 审计写入失败（业务回滚） | 是 |
| E1011 | 尝试修改审计记录被拒绝 | 否 |
| E2001 | 审计必填上下文缺失 | 否 |

---

## 7. 失败恢复

| 失败点 | 恢复方式 |
|---|---|
| 审计写入失败 | 业务事务整体回滚（R2）；允许重试整个业务操作 |
| 审计表空间增长 | 提供归档策略：超过 N 天可导出到冷存储后**由管理员显式操作**转移，**不得自动删除** |
| 触发器误拦截 | 任何合法路径都不会 UPDATE 审计表；若确有更正需求，走"新增反向说明记录"而非修改原记录 |
